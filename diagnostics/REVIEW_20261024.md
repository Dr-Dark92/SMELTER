# SMELTER review — 24 October 2026

Reviewed revision: `3f72721` on `main`. This is a review, not an implementation change. Application code, saved permissions, production conversations, and configuration were not changed by this review. Tests used disposable state. Existing services were left running.

## Assessment

The host dashboard has substantial tested boundaries: fixed tool schemas, explicit task grants, frozen configuration, durable outcomes, filtered containers, and create-only operations. The normal Windows suites pass. However, the actual frontend/container integration fails on this revision, CI does not cover the designated main branch, and the new persistent OpenCode pool introduces lifecycle and task-isolation gaps. Passing unit tests do not establish that all advertised workflows work.

The highest-priority repairs are the missing requirements catalog in workspace snapshots, the main-branch CI filters, and the persistent pool's task/cleanup boundaries.

## Findings

### R01 — P1: Workspace snapshots omit a newly mandatory root dependency

Sources: `tools/dashboard/frontend_workspace.py:41–59`, `tools/setup/requirements_catalog.py:11–15,78`, `tools/dashboard/dashboard.py:14–15`.

`_source_files()` copies `tools/`, `skills/`, and three named Markdown files. It omits `system-requirements.json`. The copied requirements loader reads that root file at import time, and `dashboard.py` imports the scanner immediately. The same file collector feeds frontend copies, coding copies, and container snapshots.

Reproduction: the real Docker frontend smoke returns `workspace_validation_failed`, with `FileNotFoundError: /workspace/system-requirements.json` in tests importing the dashboard and scanner. A separate minimal copy probe reproduces the missing-file import failure. This is an integration regression despite the passing host suite.

Impact: a fresh frontend copy cannot complete its fixed Python validation or reach preview. Copied dashboard startup and code tests that import it are also affected. Not every small coding fixture needs this catalog, so do not infer that all coding tests fail.

Repair: define an explicit shared runtime/source manifest that includes the catalog and other required root resources. Use it for frontend, coding and container copies. Add a real-copy import/startup regression and rerun actual frontend and coding profile smokes.

### R02 — P1: CI filters omit `main`

Source: `.github/workflows/offline-verification.yml:3–8`.

The only checked-in Actions workflow triggers pushes to `SMELTERV1` and selected `codex/*` branches, and PRs targeting `SMELTERV1`. It omits `main` from both triggers. The current deployment handover explicitly directs work to `main`, which is also the repository default branch.

Impact: normal pushes and PRs on the designated development/release branch do not trigger these contract, browser and container checks. This explains how the workspace integration regression can coexist with historical green CI claims.

Repair: include `main` for push and PR events, verify a PR to `main` runs all intended jobs, and check branch-protection configuration separately. Remote protection settings were not inspected in this review.

### R03 — P1: Persistent model relay accepts inference without an active task

Sources: `tools/dashboard/opencode_pool.py:55–58,80–82`, `tools/dashboard/opencode_sandbox.py:102–108,147–169,227`.

Pool clients are created with `allow_inference=True`. Detaching clears `control` and `bridge`, but does not revoke inference. The model POST branch checks only `allow_inference`; `_native_response()` creates a fresh `Control` if no admitted control is attached.

Reproduction: a detached ManagedClient with `control=None` accepts a valid fixture model POST and reaches the mocked native inference handler. No live model call is needed to demonstrate the missing admission gate.

Impact: if a late/queued request remains after abort/release, the persistent worker can invoke Ollama outside the task's cancellation and durable lifecycle. Queue packets carry no task/session generation, so attaching another task also lacks a packet-level stale-request guard. Cross-task exploitation was not demonstrated and is a risk inference, not a claimed observed attack.

Repair: require an active admitted task for model/tool packets; bind packets to a task generation; reject stale work; quiesce or replace the worker when abort completion is uncertain. Test delayed packets across release/reacquire and cancellation during a tool call.

### R04 — P1: Pool teardown detaches the bridge before its cleanup wait

Sources: `tools/dashboard/opencode_pool.py:33–38,70–85`, `tools/dashboard/opencode_sandbox.py:267–289`.

Both release and discard detach the client before calling `close()`. `ManagedClient.close()` relies on `self.bridge` to close the bridge and, for an active operation, wait using `bridge.cleanup_wait_timeout()`. After detach, it sees no bridge and uses only the generic 15-second thread wait.

Reproduction: a fake client records `close_had_bridge=False` when unhealthy release closes a client that previously had an attached bridge. Source inspection confirms the production close path loses both bridge closure and its active-operation deadline.

Impact: an already admitted fixed tool can outlive that short wait. Cleanup may fail and final receipts can be sampled before the operation finishes. This is particularly relevant to cancellation while an MCP operation has a longer registered deadline.

Repair: retain task/bridge ownership through quiescence and receipt collection; detach only after shutdown or explicitly pass the old bridge to cleanup. Add an in-flight delayed-operation regression. The long-running receipt-loss outcome was not exercised against production state.

### R05 — P2: Replacement proceeds after container cleanup reports failure

Source: `tools/dashboard/opencode_pool.py:33–38,47–52`.

`_discard()` clears the stored client/key and returns `close()`'s cleanup result. During acquire/replacement, the caller ignores that result and starts another client.

Reproduction: a fake old client returns `False` from cleanup; changing the model still creates a new client and reports the pool as `busy`.

Impact: an old container/run can remain while the pool proceeds as if replacement succeeded. Ownership metadata may permit later reconciliation, but the pool has lost the old handle and does not surface the failed replacement cleanup at admission.

Repair: block replacement and report cleanup pending until removal is confirmed or explicitly reconciled. Test failed close on model, policy, image and tool-manifest changes.

### R06 — P2: Session warm-up bypasses the component enable gate

Sources: `tools/dashboard/dashboard_api.py:81–90`, `tools/dashboard/opencode_pool.py:90–110`, `tools/dashboard/component_controls.py`.

The session-start API calls `pool.start()`, which constructs a ManagedClient without calling `component_controls.require_enabled()`. The ordinary chat admission path does check the component. System status Stop changes a configuration flag but does not stop the persistent pool.

Reproduction: patching `require_enabled()` to reject use still lets mocked `pool.start()` reach `ready`, with zero calls to that gate.

Impact: selecting OpenCode or retrying its status chip can start a resource-consuming container while System status says the component is stopped. This does not bypass the separate chat admission check or directly grant host tools.

Repair: share lifecycle admission between component controls and pool start; have Stop actually stop the idle pool. Show the real pool state in System status instead of the older 'on demand/one container per task' description.

### R07 — P2: Installer can exit successfully with required steps blocked

Source: `tools/setup/install_missing.ps1:237–240,289–290`.

When no executable setup actions are available, the script prints blocked prerequisites, writes defaults, and exits zero. At the end of an installation run, only entries labelled failed affect the exit code; blocked required steps are not failures in that result calculation.

Impact: deployment automation can treat an incomplete selected profile as successful. The printed plan is more truthful than the process result. This was established by control-flow inspection; services were not stopped to force this state on the user's machine.

Repair: give non-dry-run blocked/incomplete profiles a distinct nonzero exit status and a machine-readable summary. Preserve a successful exit for a purely informational dry run if desired. Verify post-install readiness before claiming profile completion.

### R08 — P2: Web setup child processes have no execution deadline or shutdown owner

Source: `tools/setup/setup_web.py:127–135,188–198`.

The web install and vanilla setup paths start subprocesses directly, read stdout until EOF, and call `wait()` without a timeout. Their worker threads are daemon threads. These paths do not use the dashboard's bounded process runner and do not retain a cancellable process/job owner.

Impact: a hung installer or child retaining stdout can leave setup 'running' indefinitely; closing the web service does not establish child cleanup. This is an existing documented lifecycle concern, still present in this revision. No real installer was intentionally hung during review.

Repair: explicit process ownership, bounded duration/output, cancel/status endpoints and reliable shutdown cleanup. Test a stalled process and a descendant retaining pipes on Windows.

## Documentation and verification debt

1. **Mixed historical/current instructions.** REQUIREMENTS.md still introduces the SMELTERV1 baseline and includes legacy branch/console commands; the current README says `main` and dashboard. WORKFLOWS.md includes old JSON persistence and deferred agent claims that no longer describe the active SQLite/managed route. Add explicit historical banners or move these sections into an archive.
2. **Persistent-session docs are inconsistent.** System documentation describes fresh per-task sessions/containers and System status still says one container per task, while the current implementation keeps a container for up to eight hours. Fresh OpenCode conversation sessions and a persistent container are different lifetimes; document both.
3. **Readiness is fragmented.** Catalog/installer, startup checks, component controls, sandbox status and provider checks each answer a different readiness question. A component can be installed/enabled while a complete feature is blocked. The existing deployment plan already acknowledges the missing unified readiness/checklist.
4. **Known full-smoke model limitation remains.** The full home smoke still hard-requires `qwen3.5:9b`, although deployment supports 4B and 35B profiles. This is already recorded as open in the current next plan. Test the configured model or make the restriction explicit in the command's output.
5. **Dependency reproducibility remains partial.** OpenCode's direct version and MCP SDK are pinned, but Docker bases are mutable tags and transitive dependency sets are not fully locked. Installed immutable image IDs protect a given configured run; they do not make rebuilding the image reproducible.
6. **Prior green CI evidence is revision-specific.** Older source hashes, graph snapshots, test counts and laptop hardware state in handovers should not be treated as current desktop acceptance. The current observed Ollama version remains 0.40.7 versus the catalog's 0.40.10 expectation.
7. **Skipped and unrun checks remain material.** Eight dashboard skips, Linux-native execution, actual browser/mobile layout, live Qwen/OpenCode performance, real REA/Ghidra/media inputs, remote branch protections, and full restore/disaster-recovery acceptance are not established by this review. Existing unit and isolated smoke coverage should not be expanded into those claims.

## Recommended repair order

1. Fix R01 and R02 together; require the real frontend smoke and both coding test profiles on PRs to `main`.
2. Repair pool task binding, abort/quiescence, active-operation receipts and cleanup refusal (R03–R05), with delayed/cancelled consecutive-task integration tests.
3. Unify component lifecycle and readiness (R06), including actual persistent-container status and a working Stop operation.
4. Make installer completion reliable and bound setup children (R07–R08).
5. Reconcile current/historical documentation, lock rebuild inputs, then complete visual and live-model acceptance on this desktop.

No product fixes, commits, pushes, dependency downloads or production chat tasks were performed as part of this review.
